# Mid-workout plan edits keep the record

Gyms don't cooperate with plans: a rack is taken, a machine is broken, a set feels good enough to add a finisher. So the exercise list is editable while a workout is `in_progress` — `logging.addExercises` / `replaceExercise` / `removeExercise` — relaxing ADR-0003's "structure freezes at start". These stay fine-grained `logging.*` mutations (the builder's whole-document `workouts.update` is still `planned`-only), but they return the whole `WorkoutDoc` because a structure change reshuffles ids the client can't predict.

The hard part is a slot you already logged work in. Erasing it would delete work the user actually did, and re-attributing those sets to the movement that replaced them would make the numbers lie. Instead a slot with completed sets is **dropped**, not deleted: `workout_exercises.dropped_at` is stamped, its *unfinished* sets are deleted (a plan, not a record), and it vanishes from the live screen while staying in the document — so it reappears in the finished workout's summary/history, tagged, with its volume counting normally. A slot with nothing completed has no record to keep, so it is deleted outright. Dropped slots are frozen: no set or structure mutation touches them again.

Added and swapped-in exercises are prefilled from the user's last completed performance of that movement (falling back to the builder's 3 × 8 at bodyweight), which is the only prefill that beats asking someone mid-set to type numbers. Rejected: keeping the old slot's sets on a replacement (mis-attributed volume), clearing their completion instead (loses the record of work done), and blocking edits with logged work (the "rack is taken" case is exactly when you need it).
